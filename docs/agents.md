## 登记和更新

- 新代理开工前通过 PR 添加唯一 `Agent-ID`、显示名称、角色、状态和责任范围。首次身份登记 PR 可填写 `REGISTER:<Agent-ID>`，且只修改身份登记及其必要索引；合入后才可认领并实现功能需求。也可由 Codex 或用户先将代理登记到主分支，再开始功能工作。
- 身份登记 PR 同样适用独立子代理审核和作者自行合入规则；首次登记的代理尚未有 Agent-ID 时，reviewer 使用临时身份 `REGISTER-REVIEW-PR-<编号>`。
- 代理只能认领 `docs/requirements.md` 中无负责人的“待认领”需求；也可以由 Codex 或用户在该列表明确指定。
- 截图或聊天中明确的认领由 Codex同步进需求表与 GitHub issue/PR；拆分后的负责人仅对记录中注明的切片负责，不自动拥有整个大需求。
- 有多个代理竞争同一需求时，Codex 通过台账/PR 明确唯一负责人，并将其他工作拆成不重叠子项；需求含义有分歧时交用户决定。
- 状态只使用“活跃”“待分配”“暂停”“离开”。人员离开时保留历史身份，不删除已合入贡献的记录。
- 不在此文件记录密码、令牌、私钥或个人隐私。GitHub 账号和团队权限在 GitHub 管理，不能由 Agent-ID 推断。

## 独立子代理评审

- 每个准备合入的 PR 都必须由实施者之外的独立子代理审查最终 commit；PR 作者不能审核自己的改动。
- 每次评审使用可追溯的临时身份 `PARENT-AGENT-ID-REVIEW-PR-<编号>`，例如 `GROK-CONTRIBUTOR-REVIEW-PR-21`。此临时 Agent-ID、评审结论和审查的完整 SHA 写在 PR 中；评审者本身应按项目代理约定由父代理单独启动，不能与实现共用一个推理上下文。
- 子代理给出问题时，作者修复后必须对最终新 SHA 再审。所有问题关闭、项目检查通过后，PR 作者可自行合入；Codex 的整体复核是补充保障，不代替此审核。

## Codex 维护者协作约定

- `CODEX-LEAD` 与 `CODEX-LEAD-ASSISTANT` 保留各自独立身份；分支、PR、认领和交接均写实际 Agent-ID。
- 双方职责范围相近，协作不依赖同时在线。推进前读取需求表、台账与开放 PR；按明确边界分工，交接记录写清负责人、文件范围、依赖、验证结果和未完成事项。
- 另一方暂时离线不改变已登记的 Owner。需要继续其实现时先在仓库记录显式交接或拆分；原有 PR 和提交保留，不强推或覆盖。
- 共同遵守独立子代理审核最终 SHA、PR 合入及产品决策边界；职责相近不豁免审核。

## 信息同步方式

代理之间的项目沟通通过 `docs/requirements.md`（认领、状态、阻塞）、GitHub PR（实现、独立子代理审核和评审记录）和 `docs/decisions.md`（决策、变更、发布）完成。新的用户指导先进入台账，再同步到策划基准；不要依赖另一个代理无法访问的聊天记录。
