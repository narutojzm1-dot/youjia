# 日版本节点与每日邮件

用户于2026-10-03明确要求：每小时全天推进，每天最后一轮作为日版本关键点，系统梳理各方内容、能发布的就发布，形成版本节点文档并发邮件日推。依据与历史见[决策记录](../decisions/DAILY-RELEASE.md)，协作入口#146。

## 时间与节点责任

- Asia/Shanghai北京时间23:00计划轮次为日版本节点；即使结束时跨日，归档仍用原计划日期。每小时常规轮次继续，但此轮以整体验收、集成、发布和交接为主要交付。
- 所有活跃贡献者把节点当作版本关键点：在对应issue/PR准备当前Owner、范围、精确head、独立审查、测试/体验/资源证据、可发布状态与阻塞、下一步。无法参与或未完成如实写明，不因缺席自动转移Owner。
- CODEX-LEAD主持版本梳理与集成；CODEX-LEAD-ASSISTANT按明确交接协助。GAME-PRODUCER确认方向及用户待决材料；ART-DIRECTOR审资源与视觉一致性；ENGINEERING-SUPERVISOR审架构/兼容/风险；GAME-QA提供实际覆盖、缺陷与复测。以上不替代每个PR的独立最终SHA审查。
- 不要求所有代理同时在线才能发布已合格内容；缺失必要审核/体验证据的具体项延后。既有认领保持，开发者不因节点压力私自接管或强推他人分支。

## 系统梳理与发布

1. 查上一轮/当日日结是否仍在运行或已完成，避免并行集成和重复发布；重新读取main、开放PR/issues、需求/决策/策划、最新QA与交接。
2. 列出本日代码与架构变化、玩法已决/待决、已接入与候选美术/音频、平台/存档兼容、QA覆盖与缺陷，以及各Owner的可发/延期内容。已合入不等于已发布，资源候选不等于已接入，静态检查不等于实玩或听验。
3. 对可发布项完成必要修复/集成，精确最终SHA独立审核及所需回归/Web/体验验证全通过才合入；处理共享文件冲突并保留各方改动。延期项记录Owner、原因、依赖和下一步，不为赶日结降低门禁或批准新玩法。
4. 对已审main执行现有验证、Web导出与Pages发布工作流。运行时代码合入已触发的同一轮流水线可作为本次发布，无需重复dispatch；纯文档日也进行一次当日发布轮次。检查发布实际采用的source SHA；中途main变化不得把旧流水线当新head通过。
5. 等待Actions与Pages完成，读取公开release manifest，实际下载公开PCK并核对源构建/实际哈希（与gh-pages一致），检查必要公开入口；结果留痕。失败保留上一个可用版本，报告失败阶段和补验，不说新版本成功。不得为重发日版本绕过验证。

## 版本节点文档

每次生成`docs/releases/YYYY-MM-DD.md`，按仓库独立分支/PR/最终SHA审核规则合入。文档至少包含：

- 节点日期/时区、主持人、计划轮次和完成状态；精确源码SHA、构建号、试玩地址。
- 纳入的PR/需求与玩家影响；资源仅候选或已接入分别标注。
- 系统梳理结果：代码/架构、玩法、美术/声音、QA覆盖及未覆盖、平台和存档风险、各Owner交接。
- 延期项目、原因、Owner/下一步；真正待用户决定的材料与推荐。
- 回归、浏览器/体验证据、独立审查、Actions/Pages链接、公开manifest/PCK字节与SHA256及核验时间。
- 对上一可用版本的影响、仍存在的问题、后续计划，以及邮件状态（待发送/已发送/失败和时间；不公开私人邮箱）。

可先把发布实际结果写到关联仓库评论，再补版本文档PR；文档晚于发布时明确两者SHA，避免为了让文档包含自身最终SHA而循环发版。日结文档不覆盖历史证据，后续更正留追记。错过23:00或发布未完成时下一轮补齐并注明延迟；同一日期不重复发相同日推。

## 邮件日推

用户已授权通过已连接Gmail发送给认证账户本人。每个日版本节点完成后发送一封简短邮件，附版本节点文档、试玩、重要变化/风险和需要决定的事项；节点发布受阻也发如实阻塞报告。日推不受“只有重大进展才发邮件”的常规限制；同一里程碑合并通知，普通小时小改动不逐项发信。

收件人使用会话内已授权连接，不把地址写到公开仓库；记录节点/构建已通知与时间供去重。发送API成功只记发送成功，不声称用户已阅读。邮件连接失败保留报告并在会话说明，不虚构送达。

用户已说明美术督导定时由其处理，历史暂停快照不再作为当前不可执行依据；核对最新运行与实际回执，PM不代改其他任务。

## 开发展开与版本收敛（用户2026-10-04纠正）

每天循环“版本完成→开发展开→临近节点收敛→阶段性交付”。版本完成后的首轮，PM依据已授权方向、体验缺口和Owner能力衔接新需求与有边界的实现切片，写Owner、完成定义、依赖、验收与下一轮产物，维持有意义的可执行队列。重要未决玩法交用户；不凭数量造工作，也不把控制在制解释为全天禁止新分支。

临近下一版本时，从已推进分支中尽早确定少量当天交付目标，集中实现→精确SHA独立终审→必要验证/体验→合入；玩家可见项另接正式发布核验。优先收尾接近完成的已授权工作，暂停分散主交付的非必要开项。20/21/22点为检查点而非首次定目标；按实际进度和剩余轮次切换阶段。长期研发Draft与延期保留，不自行删除有效分支，不降低质量门禁。每项目标明确下一轮具体产物、审阅/资源/QA顺序、解除条件与接收回执；留言不代表已接收。日结说明实际闭环、未完成原因、在制分支是否减少及遗留下一步；文档/实验不默认冒充功能交付。
