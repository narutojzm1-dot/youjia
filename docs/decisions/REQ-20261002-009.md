## 设计目标：把一幅画变成能停留的小院

> 不把小院做成到处闪烁的按钮，而让玩家在**真实可见的地点**稍微走近、看一眼或做一个轻动作，就得到**这个地点自己**的独特回应；偶尔发生的惊喜是可错过的生活，不是待办清单。

成功的空间互动需要同时成立：画面里认得出对象、玩家可以安全靠近、HUD/键盘/指针说的是同一对象、互动确实发生、原地有一幅合乎画风的回应、玩家可以立即离开。至少两种彩蛋要有**不同的触发语义和绘画表现**，不要六个地点都只冒相同爱心。彩蛋可以在正常走动和偶尔驻足中遇见；不规定必须挂机等待、特定游戏日、反复刷概率或记下错过次数。若做会话内去重，只为防止短时间刷屏；不做签到、强制收集或奖励经济。

## 建议的交付顺序（每一项可独立回滚）

### 第一切片：窗台花箱 + 蝴蝶的轻发现（优先）

**价值：** 玩家刚入院即可看到房屋，却只能走过。现在让窗台附近第一次“答应”玩家；一只偶尔停花的蝴蝶把美术与彩蛋融合，不加新地图。基础互动为站在门外可达位置**主动看看花箱**，得到只属于窗台的短时水彩花影/花叶回应；蝴蝶是一种独立但可选的低频偶遇，在正常走近或观察时才可能出现，并不需要材料、等待游戏日或携草。两种反馈必须区分，彩蛋的具体时机由现场体验调节，不写硬性概率或奖励。需要小尺寸透明手绘植物/蝴蝶画作，若画风不合格宁可暂停该切片，而不以程序图标冒充绘画。

**验收：** 指针点到可辨花箱时，角色只走向门外安全站位；靠近时 HUD/行动按钮/键盘显示同一个“看看花箱”目标。实际成功才显示局部回应且约 1–2 秒内淡出；未命中、离开或改点其它目标不误播、不消耗草/鱼、不中断散步。蝴蝶不进入相册/存档、不挡 UI，低动效仍能以一帧静态画被看见；不出现“开门/进入室内”误导。新旧档均无需迁移。

### 第二切片：岸石拨水 + 水面惊喜

**价值：** 与花箱的“观察”不同，这里是主动触碰水面；水纹不是鱼、也不是投喂。玩家选中**岸石而非整片池水**，可短暂拨水，看见写在当前水面上的透明手绘涟漪；一个偶尔出现的轻微水面惊喜（候选蜻蜓）提供另一种意外。优先验证岸石目标是否足够大且不覆盖已有钓鱼命中；如果画面不支持两者清晰区分，应改为显式次级入口，不能直接覆盖钓鱼。

**验收：** 池面继续钓鱼，鸟继续投鱼，鱼在手/抛竿中不被新操作抢占；岸石命中后所见、所按、HUD 目标一致。成功有可读的水彩回应，未命中和取消无“抓到鱼”假反馈。蜻蜓只作为无收益的观察彩蛋；低动效静止可读，所有结果不改鱼种/咬钩窗口/库存/相册。旧存档可直接进入，无新增持久字段。

### 第三切片：栅栏边观察 + 棚檐小动静

**价值：** 把远景中最显眼但玩家到不了的围栏变成“在门前看一眼”，而不是承诺新地图。可选在棚檐掠过的一片羽毛/暖光作为另一个物件感彩蛋；若门/棚在当前视口太小、目标难点准，则**后移**，先做前景石径蜗牛。

**验收：** 可达站位停在围栏内侧，指针/键盘/行动按钮统一标为“看看栅栏边”；短时反馈后及移动/暂停/切目标时，视角与控制恢复原状。不打开或穿越背景门，不进棚，不影响羊回栏；对低动效、窄屏及存档无负担。彩蛋属于场景而非每日任务。

## 跨切片交互契约

1. **发现性：** 只在当前真的可做时给克制的靠近提示；触屏/鼠标命中与脚边站位均需在人可走的院子里，候选目标与动物/钓鱼/种植有明确优先级，不让“点哪儿都算互动”掩盖失败。
2. **一致性：** 使用现有 `YardInteraction.action(target, point, label, reach)` 语义，指针点选、HUD 行动按钮和空格共用同一目标；移动取消、暂停、远距、切目标时不出现虚假成功画面。任何新的背景热点都不能拦截原有草、鱼、花与动物动作。
3. **绘画与音画：** 需新增真实水彩笔触/完整角色画帧时说明成本并记录来源、透明度、接地与低动效。音效可克制存在但不能替代看得见的对象回应；不把背景拉伸成“动态新帧”。
4. **无压力彩蛋：** 地点各有不同意味——蝴蝶停花、水纹变奏、羽毛轻落、小径蜗牛、动物互看；避免机械复用同一爱心与固定台词。不强制玩家静止指定秒数才有“资格”，不出现“彩蛋进度 0/5”。会话内节制可防刷屏，但不能成为资源、日历、签到或错过惩罚。
5. **验证与发布：** 每个切片校验成功、超距、被已有动作抢占、取消、低动效、移动与旧存档；原生渲染截图验证画风/锚点，发布后的 Web 实玩验证能点到、能离开、没有错路。独立评审最终 SHA，按仓库现有 Pages 流程交付；本提案本身**不改变游戏行为**。

## 不在此阶段的方向

不实现开门进屋、扩展地图、货币、制作、奖励、每日任务、离席惩罚、离线成长或新相册收集门槛；这些会改变玩家承诺。天气/季节可为偶遇提供美术变化，但 [REQ-005](../requirements.md) 当前尚未完成晴/阴背景复核，不能把特定天气当第一批彩蛋的必备条件。`REQ-001` 主角动作/步态仍由其原负责人推进，本提案不修改其代码。方案的正式目标动作命名、可达锚点和美术帧数在各独立 PR 中根据真实画面校准，不将本文当作已经实现的承诺。
