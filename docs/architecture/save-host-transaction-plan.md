# 存档宿主事务方案（#149 / #150）

Owner：CODEX-LEAD。基线 main 41ebba7；状态：工程方案待联合评阅，未冻结、未实现。探索核心继续由CURSOR-CLOUD负责，本方案不合入PR176、不定义正式物品或新玩法。

## 现状与目标

SaveStore v5的setter直接修改`_data`再调用同步`save()`；部分返回bool，部分丢弃结果。PR175仅验证临时文件、保留备份并恢复可读JSON对象，不包含校验代次、内存提交事务或IndexedDB确认。不得把现有save true当作Web持久化凭证。

目标是保留玩家当前照片、关系和生活进展，同时使探索所得、提交序号和旅程记录同代提交。玩家可以安全回院；失败不强迫停在院外、不加入损失或绩效机制。断电前从未确认的数据不能承诺已保存。

## 状态与职责

- `working`：当前合法院内工作状态，含尚未保存改动；每次变化递增工作revision。现有生活反馈可继续出现，不能伪称已持久化。
- `confirmed`：最近经当前平台适配器确认的完整快照、generation与内容摘要；探索去重只看这里的凭证。只读副本，不能由setter直接修改。
- `in_flight`：唯一写入身份、冻结的候选字节/摘要、捕获的工作revision、旅程ID/提案revision与预期父generation。跨平台确认前不得改变候选内容。
- 串行协调器统一管理院内保存、探索阶段保存和授予提交；排队的提交只存身份，到队首重读核心状态与提案、重查已确认水位。普通保存可合并待写请求，不复用过时快照。
- 平台适配器返回`confirmed / rejected / unknown`。接口名称仍为候选；业务不直接调用浏览器文件系统或各自写文件。

## 一笔提交

1. 队首核对当前绑定旅程、pending状态、提案revision及confirmed水位；陈旧请求无状态修改。同身份在途请求合并。
2. 校验正式目录，按探索契约处理拒绝项；不在本方案选定物品。
3. 深复制当前working，加入本次授予、水位、同一会话记录，生成完整候选。授予在成功前不对玩家发布；已提交的持有物由宿主单一入口管理。
4. 提交不可变候选；等待期间院内变化只修改working并递增revision，不修改候选、不另开写入。
5. 确认成功：更新confirmed；对working只应用本次授予及系统凭证，不整份替换。仅清除被该候选覆盖且未再变化的脏状态；有更新revision则重排普通保存。通知核心成功后再释放队列。
6. 明确拒绝：不发布授予，不改变confirmed，保留院内working和脏状态；按契约通知可重试失败。先确保底层写入已结束且不能迟到成功，再允许下一笔。

授予目标字段在提交期间禁止其他入口写入；若未来布置/消耗要改同一持有状态，也必须进入该协调器，另行定义冲突操作，不能用“回调加一次”掩盖并发覆盖。

## 未知结果不是失败

必须区分两层通知：

- 平台已确认、宿主已发布confirmed，但给核心的通知丢失：按契约空闲兜底重新入队，凭同旅程已确认水位收尾，不再授予。
- 平台完成通知丢失、超时或上下文中断，无法确定持久化结果：转`unknown`，保留in_flight身份和候选，阻止后续持久化写入、自动重发授予及新旅程分配。院内合法操作可继续留在working；清楚标识未保存，不宣称恢复所得。

不能用当前user://内存文件读回解除unknown。平台适配器必须提供可信持久化存储读取，并证明先前写入不可能在核验后迟到提交：达到静止状态后，若持久化候选身份/摘要匹配则确认成功；若仍是可信父代且旧操作已确定终止，才可记拒绝并重试；其余情况保持unknown/隔离。无法提供该证明时保持门禁，不用超时猜测。浏览器具体API、Godot桥接与事务完成信号先做平台技术验证，再冻结；本稿不承诺引擎已有这个接口。

## 同代恢复与兼容

候选方向为版本化保存封套：generation、父代身份、payload字节摘要和完整payload；摘要针对确定字节串计算，避免JSON键顺序/浮点重序列化歧义。generation须有有界整数与溢出拒绝规则，在实现前定稿。摘要检测意外损坏，不是防篡改或防玩家回滚证明。

v5迁移只能在用户文件备份、字段兼容和验证通过后执行；新探索字段尚未写入玩家档。恢复先选择整份可信提交，禁止拼接库存与另一代watermark。未来版本原文、隔离记录及诊断需跨普通保存保留，不能由现有sanitizer丢弃；未知格式保护在迁移上线前完成。两份均不可信时冻结探索自动提交并保留原始文件，不重置用户全部院内进展，不宣称已恢复。
