# 动物关系与行为模型（设计提案）

状态：架构设计中；尚未批准实现通用框架。
关联需求：REQ-20261002-011 / issue #45
Owner：`CODEX-LEAD`（模型与切片拆解）

## 要解决的问题

让动物之间的亲近、回避和冲突有可理解的来由，并允许玩家的长期相处在之后留下细微回响。关系要能支撑动物自己的日常行为，不成为显示在 HUD 上的好感度分数、收集任务或登录惩罚。场景和动物的随机性仍是世界的一部分。

例子“大鹅与马容易争执、和草泥马相处融洽”是产品给出的行为假设，不是固定脚本或已批准的具体角色设定。

## 建议的领域边界

将系统分为三层，避免把关系、动画和剧情塞进一个动物脚本：

1. **个体与倾向（相对稳定）**：动物个体 ID、物种、性格标签，以及少量可配置的物种/个体初始倾向。倾向提供行为权重，不直接决定每次结果。
2. **关系记忆（稀疏、长期）**：只为发生过有意义接触的主体对保存关系变化或记忆标记。动物对动物与玩家对动物属于不同关系类型；不因时间流逝或玩家离线自动衰减。
3. **情境行为（短暂、可打断）**：由关系倾向、当前活动/需求、地点可达性、距离和冷却共同决定一次候选互动，再交给现有行为/动画表现层执行。关系系统给出“为什么可能发生”，不直接控制 Sprite、寻路或镜头。

关系倾向不是行为命令。有效行为权重应由关系和当下条件合成；冲突需要合适距离和可用空间，亲近也不会让动物永久黏在一起。玩家不在场时照常允许场景偶遇，但不得给玩家制造错过惩罚。

## 关系记录建议

- 关系以主体对为单位，并保留方向性：A 对 B 的信任/警惕可能与 B 对 A 不同。存储层可用规范化 pair key 降低重复，但语义上不能强制对称。
- 第一版只保留少数有玩法解释力的内部维度，例如亲近/舒适与紧张/警惕；不要暴露数字给玩家，也不要为了“完整”引入泛化情绪向量。
- 初始倾向优先由配置规则提供（物种组合 + 个体特质）；实例记忆仅记录与默认不同、且足以影响后续行为的少数变化。没有发生有意义互动的主体对不必创建记录。
- 玩家关系与动物关系分开建模。喂食、抚摸或帮助动物是带来源的关系事件，再由规则更新玩家—动物关系或动物对之间的记忆；不能因一次普通点击同时全局提升所有关系。
- 有故事意义的事件应记录可读的原因标记（事件类型、相关主体、版本/时间），但第一版不需要无限事件日志或通用剧情 DSL。具体存储可在切片设计时结合现有 SaveData 结构确定。

这些字段是概念模型，不是最终 schema。写代码前需检查当前动物身份、SaveData 版本迁移与既有行为调度方式，确认 ID 稳定性和迁移成本。

## 行为选择建议

对每次社交行为，先筛选合法候选：主体在场、目标有效、距离/地形允许、双方不处于不可打断动作、冷却已结束。再根据关系倾向、性格、需求与近期重复惩罚计算权重，使用场景随机源抽取一个候选；没有候选时继续原有散步/休息行为。对双方同时有意图的互动，用一个 encounter 仲裁结果，避免两个独立 AI 对同一冲突重复开场。

每个 encounter 应有明确生命周期：`candidate → approach → interaction → resolve → cooldown`，每一步都能被移动、离开范围或更高优先级的现实需要中断。逻辑结果（例如关系事件或“刚刚争执过”）只在明确的 resolve 节点提交，避免半途退出也写成长记忆。

重复控制使用短期冷却和近期事件抑制，不用每日任务或硬性配额。随机种子/选择顺序须可在调试记录中复现，以便查找“为什么刚才发生了这次争执”；玩家体验不需要解释数值。

## 玩家可感知的回响

关系改变需要通过世界呈现，而非关系面板：之后更愿意靠近、保持距离、共同休息、出现短暂争执或和解等可观察差异；必要时配合轻短文字/照片题词。单次行为只改变可能性，不保证立即演出某段故事。表现应稀疏、自然、可跳过，不占用玩家操作，不因没有看到而丢失状态。

动物关系事件属于 Manus 的动物姿态/互动反馈内容范围（REQ-004 / REQ-008 / REQ-013）；本架构由 Codex 定义规则与接口，不覆盖这些表现切片。缺少双方动作姿势/表情/音效时，应开资源 issue，不能只用数值状态宣称行为已可读。

## 持久化与兼容

- 仅持久化长期关系记忆和已确认的故事标记；当前位置、接近目标、当前 encounter 与冷却等瞬时状态应重进场后重建。
- 老存档缺少关系字段时按物种/个体默认倾向初始化，不重置玩家既有进度。迁移必须幂等，重复读写不能累计变化。
- 新关系写入要有上限或稀疏策略，防止随所有动物两两组合形成无意义的 O(n²) 全量存档；仅实际互动过的主体对落盘。
- 玩家行为和关系事件要能从来源追溯，避免相同事件因重复回调应用多次；具体用事件 ID、一次性标志或已有存档模式需在实现切片确认。

## 首批验证切片（建议）

不要先建完整关系编辑器或通用故事引擎。先挑一对已有动物和一个可重复观察的社交行为：

1. 配置层给这对动物不同于普通漫游的初始倾向；在合适情境下偶尔出现一个已有/新增的短互动。
2. 选一个清晰的玩家行为作为关系事件来源；之后该互动发生概率或相处方式出现轻微变化，但不承诺每次都播放。
3. 证明离开/重进场及旧档加载后状态正确，场景中仍可自然散步，观察和拍照可打断。
4. 先用已有姿态资源评估是否足以读懂行为；若冲突/和解不清楚，另开美术/动画需求并在资源可用后再扩大实现。

具体物种组合、互动原因、变化幅度和玩家行为要在检查现有角色与资源后确定，不在此文档擅自定案。

## 实现前检查与验收

- 查清现有动物 AI、动画状态机、ID 生命周期、SaveData 版本与自动保存入口，确定新模型接入点；避免把调度器放入 `main.gd` 或扩张 `FeltActor` 为剧情容器。
- 记录每个候选的选择理由（调试可见即可），验证关系只是权重因素，不会绕过目标有效性、行动优先级或空间约束。
- 验证同一事件不会重复应用、双方不会重复触发、退出时状态一致、旧存档可读写。
- 验证低动效、Web 帧率和画面表现；要求玩家能从动作/距离/文字至少一种方式理解关系变化。
- 产品验收看自然度、可读性和“玩家行动留下了一点回响”的感受，不以互动次数、关系值或连续登录衡量。

## 代码现状核查（2026-10-02）

- `YardWorld._spawn_cast()` 用固定配置创建 `llama`、`goose`、`horse`、`sheep_a/b`、`duck_a/b/c` 等 actor ID。当前个体身份在代码中稳定，但重命名时存档记忆需迁移；不能用数组顺序作为身份。
- `FeltActor` 直接持有移动状态 `wander/graze/rest/lead`，负责目标点、寻路和绘制姿态；没有社交 encounter 状态或关系控制器。动物位置不写入存档。
- `YardWorld._world_snapshot()` 将附近对象压缩为**物种名**列表，丢失具体个体和方向；该快照供表情/拍立得规则使用。
- `ExpressionCatalog` 按优先级每隔约 1.6 秒匹配天气、物种邻近、玩家即时动作和可见距离，再调用 `_apply_rule()` 改表情、吐口水或拍立得。它属于表现/收藏触发器；不能直接扩成关系引擎，否则关系判断会继续与相册首拍、表情时长和副作用耦合。
- `SaveStore` 当前 `SAVE_VERSION` 为 4，按白名单读取照片、假期日数、植物和钓鱼字段，未保存动物个体状态。缺少字段的旧档用默认值，自动保存约每 60 秒；已有 setter 会立即写盘。
- 角色资源目前包括鹅的 alert/calm/rest 三种画作、草泥马多张表情，以及只有一张站姿的马。尚无能明确表达马对峙/退让的姿态或成组动作；资源缺口另由 [issue #56](https://github.com/narutojzm1-dot/youjia/issues/56) 提案，不与天气资源 issue #51 混在一起。

## 结合现有代码的架构选择

1. **个体对以 actor ID 作为 key，关系可定向。** 用 `(subject_id, target_id)` 表达“谁对谁的倾向”，如 `goose → horse` 可不同于 `horse → goose`。默认资料按物种组合提供；个体差异只在实际发生后覆盖，不预建所有组合。
2. **分开配置、关系存档与 encounter 调度。** 配置资料描述初始倾向；纯关系模块根据个体对与少量已确认记忆给出倾向；独立 encounter 控制器在统一场景快照上筛选/仲裁行为。`YardWorld` 负责接线，`FeltActor` 仅暴露开始/结束行为所需的小接口，不把规则或存档塞进动物绘制脚本。
3. **显式保留 actor ID 的邻近信息。** 新关系逻辑只读个体 ID、物种、位置、当前行为/区域等快照，不沿用拍立得系统中压缩成物种名的 `nearby` 数组。首个试验动物数量很少，直接 O(n²) 配对检查足够；不需要现在引入空间索引。
4. **不复用相册冷却或 `_apply_rule()` 作为行为执行器。** Encounter 逻辑不应由照片是否首次入册决定，也不能把吐口水等副作用当成通用关系结果。表现资源经独立 action key 交给动画/动作层，拍摄系统可以旁观 encounter 再决定是否抓拍。
5. **存档先加可选字段，首次写入再提升版本。** 关系不需要保存位置、寻路目标或活动 encounter。正式实现时在 `SaveStore` 中增加经过校验的稀疏关系记忆字段；旧档读成空记忆并继续用默认倾向。只有关系格式落地后才将 `SAVE_VERSION` 提升到 5；事件写入应由一次已确认的交互触发，避免每帧保存。个体 ID 改名时提供显式 key 迁移。
6. **短期冷却留在运行态，长期记忆持久化。** 当前会话中的重复抑制、随机种子和 encounter 阶段不落盘。玩家关闭再打开游戏后只恢复已确认的关系事实，再按当前地点/距离自然重选行为。

以上是建议的 v1 接口与存档边界；初次实现应通过独立纯逻辑模块验证，不做编辑器、关系数值 UI、任务链或通用剧情 DSL。

## 推荐的实施切片

- **Slice A：关系资料与行为仲裁（由 Codex 设计/牵头）。** 只做有限样例：鹅对马的紧张倾向、鹅对草泥马的平和倾向。两个组合共享空间时，系统选出唯一的可观察 encounter；没有合法候选时动物沿用原来的漫游/休息。避开硬编码全天候冲突，不让接触变成攻击或惩罚。
- **Slice B：动作与资源（贡献者可认领）。** 以 #56 的姿态提案确认现有 goose calm/alert、草泥马表情能否读出关系差异；若不足再制作马的退让姿态或双角色短动作。作者通过独立 PR 交付，并由非作者子代理审阅。
- **Slice C：玩家留下关系回响（Codex 先定义因果，再拆实现）。** 只把一项能从画面解释的玩家照料动作写成长期关系记忆，之后改变对应行为的可能性；必须说明是影响玩家—动物关系还是动物—动物关系，不允许一次喂食无缘无故改写全院关系。
- **Slice D：持久化和回归验收。** 在 v4 旧档、v5 新档及退出/重进场景中核对记忆一致；确认 encounter 只结算一次、可被玩家操作打断、不会抢走散步/拍照优先权。

这四步仍是架构顺序，不意味着当前已批准制作具体新姿势或确定玩家行为的关系因果；首个表现范围须结合 [#56 资源审计与姿态提案](relationship-art-proposal.md)和实际运行状态再锁定。
