# 画卷回院适配隔离原型（EXP-RETURN-ADAPTER，#200）

状态：**隔离研究原型，不是正式功能**。Owner：`CURSOR-CLOUD`。父单 #153，沿用 #156 Q10 / Q16 / Q17。

本原型只回答一件事：玩家在画卷里按「回院」后，画面怎样安全地切回小院——旧画卷的输入、相机、信号连接先全部失效再开放院内操作；保存结果未定时院内照常可走、不显示虚假「已收好」、也不能绕过持有中的保存去开始新旅程。它**不证明**物品耐久保存或强退恢复；真实宿主与 H2 / H3 / H4 由 CODEX-LEAD 推进，联合冻结前不接正式玩家入口。

## 运行

```bash
bash tools/run_exploration_return_adapter.sh test                  # 严格门禁跑隔离测试（不少于 150 项）
bash tools/run_exploration_return_adapter.sh run                   # 本机窗口试玩
bash tools/run_exploration_return_adapter.sh export                # 导出 Web 到临时目录
bash tools/run_exploration_return_adapter.sh movie OUT.avi 1280x720 # 按演示脚本录像
```

脚本与 #199 共用 `tools/lib/exploration_workdir.sh`：每次新建临时目录（运行后保留，清理用 `rm -rf "${TMPDIR:-/tmp}"/youjia-return-adapter.*`）；`PROTOTYPE_DIR` 只接受仓库外、不是 `/`、不包含仓库的绝对路径，且必须为空、不存在或由本脚本建过，校验通过后才创建或清空，创建 / 清空失败会以非零退出码报出；路径解析依赖 GNU coreutils 的 `realpath -m`。录像分辨率等参数在创建目录和导入之前校验。

## 回院顺序

画卷发出 `return_requested` 后，适配器按固定顺序执行，并写入事件记录：

1. `return_requested`：只接受当前这一代画卷、且当前确实在画卷里的请求；旧代号或已回院时记 `stale_return_ignored` 并返回。
2. 调假宿主 `go_home("player")`：核心首次冻结提案并入队；核心仍是 `active`（例如不在可回院的停留点）就留在画卷、在画卷上提示「这里还不能回院」，记 `return_rejected:<原因>`。
3. `core:pending_commit`：核心已进入待提交，开始拆画卷。
4. `scroll_input_off`：画卷清空所有按住的来源，关闭 `_process` 与 `_unhandled_input`。
5. `scroll_camera_off`：画卷相机 `enabled = false`，断开它对视口 `size_changed` 的连接。
6. `scroll_disconnected`：按连接表逐个断开画卷两个信号到适配器的连接（连接时绑定了代号，`is_connected` 认不出原方法）。
7. `scroll_freed`：移出场景树并 `queue_free()`，适配器丢掉引用。
8. `yard_camera_current`：小院相机启用并成为当前相机。
9. `yard_input_on`：小院输入从空开始。
10. `flight_started`：假宿主放行队首事务，候选写入进入「等待持久化确认」。

第 4–9 步的事件都在核对真实状态后才记录（输入与处理已关、相机已禁用且视口连接已断、信号连接表为空、已移出树并排队释放、视口当前相机是小院相机、小院输入已开），核对不过记为 `<事件>:unverified`；画卷引用没清空时 `_enter_yard` 拒绝开放小院并记 `yard_open_refused`。测试另在小院发出 `activated` 的那一刻直接检查旧画卷的真实状态，不依赖事件记录。

重复回院只导航一次：同一画卷连发、旧代号直接调用、平台返回键再调 `go_home` 都不会重冻提案或重复入队（核心已在待提交时 `go_home` 只做幂等导航）。

## 院内保存状态文字

| 核心 / 假宿主状态 | 文字 |
|---|---|
| `pending_commit`，写入在途或等待重放 | 正在收好带回的东西…可以先在院子里走走 |
| `pending_commit`，平台结果未知 | 还在确认带回的东西有没有收好，可以先在院子里走走 |
| `recoverable_failure`，可重试 | 这次没能收好，带回的东西还记着，可以再试一次 |
| `recoverable_failure`，整体内容被拒 | 有带回的东西收不下，可以空手收尾 |
| 核心进入 `committed` 后关闭旅程 | 带回的东西已收好 |
| 持有未定保存时请求出门被拒 | 上一趟带回的东西还没收好，先不出门 · ＋当前状态 |

「已收好」只在核心收到 `commit_succeeded` 进入 `committed`、且适配器随后 `close()` 成功后出现；关闭失败记 `close_failed` 而不显示已收好。关闭旅程放在收到提交结果的地方，`refresh()` 只刷新文字。原型里没有自动重试，重试与空手收尾都要按假宿主控制键，文案因此不承诺「稍后会再试」。按物品拒绝时核心去掉该物品、提案换版后继续待提交；只有整体不可重试的失败才进入「收不下」，可用空手收尾结束。已落盘但回调丢失（迟到确认）时，即使假宿主内存里已有该物品，文字仍是「正在收好」，直到队首重放按水位确认。文字只是占位，正式文案归 GAME-PRODUCER / #201。

## 体验观察

- 回院是瞬切，没有过渡；从画卷到小院的空间关系（「从院门回来」）还没有表达，留给 #201 决定是否需要淡入或院门动画。
- 结果未知、写入失败时的文字只是占位，玩家能看懂「还没收好」，但没有说明会不会自动再试；正式节奏（自动重试间隔、是否需要玩家点重试）需要 Leader 的 H2 结论。
- 出门被拒时只在状态条加一句话，没有更明显的反馈；正式小院里应由院门表现承担。
- 小院与画卷都是几何占位；小院相机不缩放，竖屏只看到很窄一段院子。
